## 5. 角色

**从 RoboRSI 借的**：审查和执行分开（它的消融里单 agent 50 个任务做成 9 个，分角色 36 个）；候选隔离、带版本、被拒的候选不能原样重交；人的纠正落成可执行的检查。
**不借的**：运行时 LLM 在环（我们的专家是 50 Hz 代码，放不下每局上百次调用）；它的验收门"开发种子上成功 ≥ 2 次"（真实成功率 50% 的候选有一半概率通过）；它的归因规则"第一个后置条件不成立的节点"（上游过了自己的判定、却把下游带出可行范围时会改错地方）。

| 角色 | 谁 | 输入 | 输出 |
|---|---|---|---|
| Manager | Claude 主会话（Opus 5.5） | 台账、预算、上一轮验收结果 | 下一步做什么；写台账 |
| Reviewer | 子 agent，每轮新上下文 | 诊断池的交接记录、轨迹、失败局视频帧、包络表 | 排好序的归因假设，每条带"做哪个干预、预计翻转哪些局" |
| Prober | 脚本 | Reviewer 指定的干预 | 每局每个干预的结局表 |
| Engineer | 子 agent，在主检出里只改两处（见 §7）；被拒就把它改过的文件恢复原样 | 被干预证实的归因 | 候选：一份配置 yaml，可选一份代码补丁 |
| Gate | 脚本，LLM 不能改判 | 候选 | 接受 / 拒绝的 JSON |

Reviewer 不看 Engineer 的推理，Engineer 不看验收池逐局。Gate 用代码而不用 LLM，因为这个仓库反复出过"配置只生效一半"和"看到数据后改阈值"。

## 6. 一轮迭代，和补上的三环

一轮：Reviewer 出假设 → Prober 跑干预 → 没有干预能翻转就回到 Reviewer；有，Engineer 把它做成候选 → Gate → Manager 记账、定下一轮。

### 6.1 交接记录

每局在每个阶段交接处记一条固定格式的记录，两个控制器用同一个提取脚本：
- 走完：沿轴站位距离、横向偏差、相对边线的 yaw、残余速度、刹车超调。
- ready：两腕误差、骨盆高度、躯干俯仰。
- reach / descend：手到目标的误差随时间、最好误差、两手共同漂移、指令和实际的骨盆高度与腰姿。
- close / lift / hold：两指接触时长、箱子倾角、抬起高度。

数据大多已在 `events`、`expert_diagnostics` 和 50 Hz 状态里，这一步是把口径固定下来。SONIC 成功局的分布就是第一版"下游可行的交接范围"。这替代 RoboRSI 的二值后置条件：上游过了自己的判定、却把下游带出可行范围的情况（crate 线站位 0.265 / 0.28 m、朝向 14° 那一类）在这里看得见。

### 6.2 控制器包络

在专家实际用到的那片区域，测"指令要多少、控制器给多少"：骨盆高度，腰的俯仰、横滚、偏航，躯干前倾，两腕位置和姿态。
- SONIC 用诊断池里已有的流式参考和实测关节算；ScaleBFM 用移植脚本记下的关键点参考和实测算。不需要新跑。
- 产物 `envelope/{sonic_v1_1,scalebfm_m22200_mode2}.json`：每个轴的交付比和饱和点。
- 用法：找出"值贴着 SONIC 的交付边界才说得通"的字段（§20 说的不交付下蹲、腰只交付一半，对应 `carry.pelvis_height_min`、`*.waist_pitch_max` 这一类），作为重标的首选，不让 agent 在 89 个字段里盲搜。

### 6.3 干预归因

从保存的状态分叉，每支只改一个量，跑到结局。
- **分叉点**：走近开始；ready 到位（`CoordinatedReach` 构造之前，配置类干预在这里生效）；descend 开始。
- **分叉的做法（10-14 改，DECISIONS）**：不存快照，从起点重跑前缀，到分叉点换成干预后的配置。前提是一局只由（起点，配置）决定；这样 IK、专家状态机、ScaleBFM 的历史都不用拷贝。代价是每支多跑一段前缀（一局约 23 s）。
- **先过分叉一致性检查**：空干预的分叉、换进程、换分片、倒序跑，10 局里结局、结束时刻和逐拍 `qpos` 都要和原局一致；再和 25.7 的逐局结果比（`phase0_checks.sh`）。
- **第一批干预**：
  - 把参考的下蹲和腰姿限到 SONIC 的实际交付值（直接检验 §2 的假设）；
  - `tracking_gain` 0 / 0.5 / 1.0；
  - 夹爪中心 + 姿态伺服打开；
  - 站位 −4 / −2 / +2 cm（真走过去，不瞬移）；
  - 走速 0.15 / 0.35 m/s；
  - 诊断池独有的上界：用 SONIC 那一局的实际姿态代替专家参考。
- **读法**：每个干预记"失败翻成功"的局数；同一干预也在成功局上跑，记"成功翻失败"。Reviewer 跑之前写下预测，事后记命中率，作为"LLM 读轨迹归因准不准"的直接度量。
- **规模**：诊断池约 34 局失败 × 6 个干预 × 约 15 s，4 进程并行约 10 min。

### 6.4 验收门（冻结）

- 候选和 incumbent 在验收池同一批起点上配对。先跑前 30 个，候选净多赢的局数 ≤ 0 就拒绝；否则跑满 60 个。
- **接受**要同时满足：
  - b − c ≥ 3，且单侧 exact McNemar p ≤ 0.05（b = incumbent 败、候选成，c 相反）；
  - 摔倒 ≤ incumbent + 1，掉物 ≤ incumbent + 1；
  - 没碰 §3 的冻结字段和路径；
  - 改动的每个字段在 ScaleBFM 这条代码路径上真的被读到（运行时记录配置字段访问），对应"先 grep 调用方再测常量"和"配置只生效一半"两条教训；
  - 候选哈希没被拒过。
- 每次验收顺带重跑 incumbent 的 5 个起点，结局必须和上次一致（确定性哨兵）。
- 验收次数写进报告：调用越多，验收池上的假阳性越多，最终数字只认封存集。

## 7. agent 能改什么

| 层 | 内容 | 条件 |
|---|---|---|
| 参数 | 未冻结的字段、ScaleBFM mode 0–7、站位、夹爪伺服、刹车前馈 | 过验收门 |
| ScaleBFM 专属代码 | 移植脚本；新的 ScaleBFM 模块，例如参考姿态重定向、夹爪伺服、停滞恢复 | 验收门 + 相关单测 |
| 共享专家代码 | `src/locomani/tasks/crate/*` | 只能加默认关闭的开关，SONIC 配置下行为不变，`make check` 通过 |
| 升级给人 | 场景、箱子、成功规则、控制器 checkpoint 或训练、位姿来源、真机、冻结规则、预算 | agent 停下写报告 |

**判不可行**：某类起点上所有干预都翻不过来，且包络表显示需求在 ScaleBFM 的交付范围外，agent 可以写"不可行"结论并附证据，但不能把这些起点从任何池里拿掉。RoboRSI 没有这个出口，它的失败只会以"预算耗尽"结束。

## 8. 人的知识怎么进闭环

- 闭环不读个人记忆目录，只读一份带版本的规则文件 `rules.md`（从记忆里挑出来）。这样"用了多少人的知识"可数。
- 能写成代码的进 Gate 或 Prober：冻结阈值、最少局数、字段访问检查、分叉一致性、只有闭环重跑才算证据（离线 IK 重解、回放记录下来的指令都不算）。
- 只能写成提示的进 Reviewer 的说明：先看逐帧记录再信失败标签；执行器门控会制造控制器之间的差异；按成功挑出来的子集复测会回落。
- 人插手全部记进 `interventions.jsonl`：时间、类别（知识 / 安全 / 纠正归因 / 修基础设施 / 改预算）、内容。闭环期间用户发的任何消息都算一次。

## 18. 接 CuRobo：从下垂直接伸到预抓（用户 2026-10-14：要自然的动作）
