### 2. LML 怎么下多路点伸手

LML 的伸手参考是"一串 IK 姿态 + 每段时长"，`blend_frames` 在相邻姿态之间按最小加加速度插值。一下伸手的流程是：
- `Planner.reach` 在起点建一个全身 IK；
- 沿直线每 3 cm 解一个姿态，速度 0.15 m/s；
- `plan_rec` 把这串姿态挂到实测骨盆上。

多路点只要把直线换成折线：
- 同一个全身 IK 依次走过各个中间点；
- 每段手腕姿态从上一个点的转到下一个点的，和 `Motor.reach` 的 via_rot 规则相同；
- 另一只手原地保持；
- 其余设置和 `Planner.reach` 一样。

开发脚本 `wbik_route.py` 的 `route_reach` 就是这样做的，不改任何共享模块。分段的记录格式里已经有 `n_via`、`via_p`、`via_r6`（最多 16 个点），是 data3b 加"绕行"段时留下的，路线可以直接记进去。

### 3. SIMPLE 的规划和障碍地图怎么搬到 LML 那一眼

做法和 SIMPLE、HA 的规划进程相同：
- cuRobo 的 G1 模型，PRIMITIVE 方块障碍；
- 起点姿态附近 1 cm、终点姿态附近 2 cm 以内的方块去掉；
- 8 个轨迹优化种子，64 个 IK 种子，最多试 4 次，单次限时 10 s。

LML 这边换掉的只有障碍从哪来：
- **来源**：那一眼缓存里的家具点（`furn_pts`，地面已去掉），在"看那一眼"的坐标系里。
- **放到哪里**：第一下伸手命令时，用机器人自己的腿部里程计位姿，把这些点放到实测坐标系里。这和 `command_b` 放目标点的方法完全相同，不用仿真真值。
- **裁剪**：只留机器人朝向坐标系里前 −0.3–1.2 m、左右 −1.0–0.7 m、高 0.03–1.8 m 的点。
- **体素**：2 cm 一格；物体点 2 cm 以内的去掉，免得把要抓的东西当成障碍。
- **方块数**：浴室约 130–170 个，客厅约 1300–1500 个，厨房约 6000–6500 个，上限设 8000。

运动学一致：用 cuRobo 的 G1 模型和记录下的关节角、骨盆位姿算手的位置，和 LML 记录的手点相差不到 0.01 mm。

### 4. 关键问题：规划时骨盆放在哪里

我们的全身 IK 在伸手时会动骨盆：
- 前倾 25–40°（到了 IK 设的上限 40°），后移 5–14 cm；
- 腰转 30–40°；
- 雕像柜还要蹲下 22 cm，腰转约 117°。

SIMPLE 的做法是骨盆固定在起点。这在 LML 上不行。ScaleBFM 的 51 局里：
- 只有 14 局规划成功（苹果、盐瓶）；
- 其余 37 局连终点的 IK 都解不出，去掉所有障碍也一样。

改成"骨盆放在我们的 IK 为预抓取解出的姿态上"：
- cuRobo 只规划腰和右臂，共 10 个关节；
- 起点用 cuRobo IK 把当前手的位姿放到这个骨盆下，从当前关节角起算；
- 终点就是我们的 IK 的预抓取姿态；
- 这个骨盆姿态是机器人自己算的，不用真值。

结果（ScaleBFM，第 30–39 局，51 局）：

| 设置 | 规划成功 | 每次耗时 | 路线长度中位数（直线 59 cm） | 中间点 |
|---|---|---|---|---|
| 骨盆在起点（SIMPLE 原样） | 14/51 | 2.8 s | 98 cm | 7–8 个 |
| 骨盆在预抓取姿态，腰锁住 | 42/51（雕像柜 0/9：起点 IK 解不出） | 6.4 s（每局要重建模型） | 102 cm | 7 个 |
| **骨盆在预抓取姿态，腰放开** | **51/51** | **2.5–2.7 s** | **75 cm** | **5–9 个** |

所以选最后一行。用同样的设置，第 30–39 局里 SONIC 48/48、HEFT 52/52 也都规划成功（活化距离 3 cm、5 cm 都是），每次约 2.5 s。路线的样子：

- 客厅和浴室只偏 5–10 cm。

## 假设

1. **H1 路线减少"路上碰家具"。** A 在厨房任务上的直线参考本来就穿过那一眼看得见的家具。cuRobo 按那一眼的点云绕开，我们的 IK 能照着走，所以 C 路上碰家具的局会比 A 少。
2. **H2 少碰就多成功，但只在能绕的任务上。** 成功的增加主要来自苹果，哑铃、浇水壶上少一些。蜡烛的碰撞在目标附近，雕像柜是 IK 够不着，路线都管不了。
3. **H3 自身模型的好处在路线上照样有。** 在 C 的基础上，预抓取和进入段用 R 的缩回反解，比 C 好（CR > C）。走路线后预抓取是一小段直线，起点已经停稳，仍在 D 训练过的范围里。
4. **H4 两者能叠加。** CR 比直线的 R 好（CR > R）。好处只来自走了路线的局。

## 做法

**分组**（每组 7 个任务 × 90 局）

| 组 | 路线 | 预抓取 | 进入段 | 来源 |
|---|---|---|---|---|
| A 直接执行 | 无 | 目标 | 目标 | lmlcmp3，复用 |
| R 缩回可达 | 无 | R 的反解 | R 的反解 | lmlcmp3，复用 |
| C 路线 + 直接执行 | 有门槛时走 cuRobo 路线 | 目标 | 目标 | 新跑 |
| CR 路线 + 缩回可达 | 同 C，同一条路线 | R 的反解 | R 的反解 | 新跑 |

- 三个控制器都跑 C、CR：3 × 2 × 630 = 3780 局。
- 新组号：C = 5，CR = 6。

**第一下伸手命令时怎么决定走不走路线**（C、CR 相同，只用机器人自己的信息）

1. **算 A 此刻会发的直线参考**：
   - 有中间点的任务（抓取点高 ≥ 0.80 m）：先伸向中间点，再从那里伸向预抓取点；
   - 其余任务：直接伸向预抓取点。

   都用我们的 IK 算。
2. **门槛**：这条参考的手臂在"路上"（手离预抓取点 10 cm 以外）离那一眼的家具方块不到活化距离（5 cm），就走路线；否则照 A 发命令。这时 C 的命令就是 A 的，CR 的就是 R 的。间隙用 cuRobo 的手臂球模型算，和开发调查第 5、10 条相同。
3. **规划**：
   - 骨盆放在我们的 IK 为预抓取解出的姿态上，腰和右臂放开，右手张开锁住，右臂和右手参与碰撞；
   - 其余按开发调查第 3、4 条；
   - 活化距离 5 cm（开发调查第 10 条）。
4. **路线**：
   - cuRobo 的手部路线按 1 cm 容差简化成中间点，最多 16 个，超过就把容差每次加 0.5 cm；
   - 记下每个点的手腕姿态。
5. **退回**：规划失败（起点 IK、终点 IK、轨迹优化失败，或超时），或者简化后没有中间点，就照 A 发命令。
6. **缓存**：同一个控制器、任务、局只规划一次，存成文件，C、CR 和以后的重跑都读这一份。到这一刻为止 C、CR 逐位相同，所以输入也相同；cuRobo 每次重规划结果不一样，这样就避开了。分片改成按局分，让同一局的 C、CR 在同一个进程里先后跑。

**走路线的局，接下来的命令**

1. **路线命令**（第 0 下，中间点直接发，不经过自身模型）：
   - 我们的 IK 依次走过各个中间点，到最后一个中间点为止；
   - 速度 0.15 m/s，每 3 cm 一个姿态，整条至少 0.6 s；
   - 发完按机器人自己的停稳规则等，最多 3 s。
2. **预抓取**（第 1 下）：从最后一个中间点到预抓取点是一小段直线。C 直接发目标；CR 用 R 的缩回反解。
3. **进入段**（第 2 下）、合手、抬起：C 照 A，CR 照 R。

## 度量

**主比较**：ScaleBFM，判定集，按局配对，McNemar 精确检验。下面两个做 Holm 校正：p 较小的那个要 < 0.025，另一个要 < 0.05。
- **P1**：C 对 A 的成功率。
- **P2**：CR 对 R 的成功率。

**机制**：
- **M1**：判定集上"路上碰家具"的局数，C 对 A、CR 对 R，按局配对。这里算"路上碰过"，不论是不是第一失败原因。
- **M2**：走了路线的局里，执行的手和手臂偏离路线多少（真值，只打分）；碰家具那一刻离那一眼的家具方块多远，用来区分"执行偏了"和"那一眼没看见"。

**次要**：
- CR 对 C；
- SONIC、HEFT 的 C 对 A、CR 对 R；
- 7 个任务全算；
- 各任务的成功数、合手距离的配对差；
- 失败原因：照 lmlcmp3 的顺序，先判"预抓取时碰到物体"，"碰家具"拆成路上、目标附近、伸手前三项；
- 走路线的比例、规划失败率、路线长度、时长、中间点数。

**判定集**：照 lmlcmp3 的规则在新组上重算，两组分开之前的失败和 lmlcmp3 相同，预计仍是蜡烛、苹果、雕像柜、哑铃、浇水壶。碗、盐瓶照规则排除：碗失败在腕部朝向的参数化表达不了掌心朝下，盐瓶失败在 SAM 3 认不出，路线都解决不了。7 个任务全算的结果作为次要结果照报。

**敏感性分析**：开发时看过第 30–39 局的 A 记录（开发调查第 1–6 条），所以去掉这 10 局（每个任务 80 局），再报一遍 P1 和 P2，配对和检验方法不变。只作报告，不改判据。

**一致性检查**：
- C 里不走路线的局和 A 逐位相同，CR 里不走路线的局和 R 逐位相同；
- 同一局 C、CR 的路线命令逐位相同；
- 路线文件的 md5 进记录；
- 冒烟时在设计种子上，C、CR 不走路线的局和 A、R 逐位相同，走路线的局 C、CR 的路线命令逐位相同。

所有碰撞、手和目标的距离都是仿真真值，只用来打分，不进任何决策。

## 判据

| 结果 | 结论和下一步 |
|---|---|
| P1 成立（C − A > 0，校正后显著），且 M1 C 比 A 少 ≥ 25 % | 路线有用。LML 抓取默认加路线；登记"完整版"（见成本），看能不能把路线上的偏差也修掉 |
| P1 不成立，但 M1 少 ≥ 25 % | 规划绕开了，但成功没跟上。先查少碰的局为什么还失败（换成了目标附近碰、抓空，还是 IK），再决定完整版 |
| M1 少 < 10 % | 路线在规划里绕开了，执行时没绕开。用 M2 分两种情况：执行偏差大于留出的间隙，完整版（路线上的自身模型）有理由做；碰的是那一眼没看见的东西，问题在地图，停掉路线这条线 |
| C − A < 0 且 p < 0.05 | 路线有害（时间长、绕得远、偏得多）。停下查，不进默认流程 |
| P2 成立 | 路线和自身模型能叠加，LML 的默认流程改成 CR |
| P2 不成立，但 P1 成立 | 路线的好处被 R 吃掉了（R 的缩回可能已经顺带少碰）。照实报告，默认流程选 R 还是 CR 看 CR − R 的方向 |
| CR − C ≤ 0 | 自身模型在走过路线以后没用，和 lmlcmp3 矛盾。查走完路线停下时的姿态是不是已经出了 D 的训练范围 |
| 冒烟时不走路线的局和 A、R 不逐位相同，或一致性检查不过 | 先停下查清，不开正式运行 |

## 成本

**本轮正式运行**：
- 仿真 3780 局，只用 CPU。按 lmlcmp3 每个进程每局的用时（ScaleBFM 53 s，HEFT 52 s，SONIC 119 s），每个控制器 35 个进程，路线每局多 5–9 s：
  - ScaleBFM 约 35 分钟；
  - HEFT 约 35 分钟；
  - SONIC 约 80 分钟；
  - 合计约 2.5 h。进程数开跑前按 CPU 负载定，少用进程就按比例拉长。
- 规划 1890 次，约 1.3 h 的 GPU 时间，一到两个进程（4090 的 1–3 号卡，每卡最多一个），每个约 1.3 GB。
- 开发（规划进程、`lrt_run.py`）、冒烟、检查和评估脚本：约半天。

**完整版**（沿多路点路线采数据，训练多路点模型）：这里只是估算，暂不登记，等用户决定。
- **采集**：每个控制器约 1.5 万次开场（data3b 的规模）。
  - 每次一条空地上的随机多路点路线，形状照本轮实测：5–14 个点，长度是直线的 1.2–2.5 倍，最多偏 50 cm，时长 2–9 s；
  - 路线后面照常接预抓取和进入段；
  - 每次开场按 data3 的实测加上路线的时间，约 20–25 s/进程；
  - ScaleBFM 50 个进程约 2 h，HEFT 30 个进程约 2.5–3 h，SONIC 在 4090b 上 38 个进程约 2.5–3 h；两台机器并行约 3 h。只用 CPU，要排在 HA 采集之后。
  - 随机路线不用 cuRobo 生成，否则 1.5 万次规划要十几个小时。
- **模型**：D 现在没有路线的输入，要改 `data.py` / `train.py`，加中间点特征，预测路线终点和沿途的手。三个控制器各 3 个种子，按 train3b 的经验约 3–5 h GPU。
- **评估**：多跑一组"路线上也修正"，三个控制器共 1890 局，约 1.5 h。
- **合计**：约 1.5–2 天（含开发、冒烟、复核），机器时间约 10 h，主要是 CPU。

**结论**：
- **不是点云范围变了**。mask 只小了约 3 %（少 3 个像素、4 个点），中位点和站位只差 1–2 mm。

- **真正的原因是苹果卡在边上**：
  - 616 个抓取里，过了朝向和可达框还剩约 24 个；
  - 苹果放在台面上、靠着柜子，这 24 个大多会让手碰到家具，最后只剩 0–6 个，中位数 1 个；

- **方向**：翻过来的有 12 局是"真值 mask 下变成失败"，5 局是"真值 mask 下变成能过"。按局配对做 McNemar 检验，p = 0.14，和随机翻动分不开。真值 mask 略小一点（SAM 3 在苹果边缘多算了一圈像素，物体高了 0.2 cm），平均剩下的抓取从 1.81 降到 1.62。这可能有一点真实的影响，但这些数区分不出来。
- **对本轮的影响**：
  - 这些局在分组之前就失败，四个组都记失败，不影响配对比较；
  - 判定集不变：苹果 15/90 不到一半；
  - 预测里苹果的分组前失败已经按 13–17 写了。

### 意外：HEFT 的 K3 照字面判为 FAIL（4 局），是 K3 截取段 0 的方式造成的（协调人同意：照字面记 FAIL，冻结代码不改）

**发生在哪 4 局**：苹果第 114 局、碗第 97 局、雕像柜第 36 和第 94 局。K3 报的是"路线命令不同"：
- 记录字段 `reaches[0]` 和 `d3[0]` 没有差异（输出里第三项是 `[]`）；
- 有差异的是分段数组：`att_err_deg`、`backend_id`、`chain`、`cmd_target`、`core`（只印了前 5 个）。

**原因**：
- 这 4 局走完路线以后，C 和 CR 的段数不同：

  | 局 | C 每段的步数 | CR 每段的步数 |
  |---|---|---|
  | 苹果 114 | [106, 43] | [106, 40, 23] |
  | 碗 97 | [105, 40, 20] | [105, 36] |
  | 雕像柜 36 | [61, 23] | [61, 69, 30] |
  | 雕像柜 94 | [66, 25, 33] | [66, 28] |

  段 0（路线那一段）的步数两组相同；后面几段本来就不同，因为 CR 的预抓取和进入要经过 D。
- K3 截取段 0 时，用的是 C 的段数（`nseg = len(z1["n_steps"])`），两个文件都按它截：
  - 每段一个值的数组（如 `cmd_target`），长度等于 C 的段数时只取第 0 行；
  - CR 的这类数组长度和 C 的段数不同，就没被截成第 0 行，而被当成按步的数组整段拿来比。
  - 所以报出来的正好是这些每段一个值的数组。
- 拿每个文件自己的段数截出段 0 再比（离线，只读）：4 局的 81 个分段数组加 8 个手臂数组全部相同。原始输出：
  ```
  apple 114 [('81 arrays', []), ('arm 8 arrays', [])]
  bowl 97 [('81 arrays', []), ('arm 8 arrays', [])]
  statue_cab 36 [('81 arrays', []), ('arm 8 arrays', [])]
  statue_cab 94 [('81 arrays', []), ('arm 8 arrays', [])]
  scalebfm routed episodes 428 C and CR with different segment counts 0
  sonic routed episodes 377 C and CR with different segment counts 0
  heft routed episodes 435 C and CR with different segment counts 4
  ```
- ScaleBFM 和 SONIC 没有一局 C、CR 的段数不同，所以只有 HEFT 出现。

**结论**：
- 这 4 局 C 和 CR 执行的路线那一段逐位相同，K3 要查的内容是成立的；
- 照 K1 的处理办法，K3 照字面记 FAIL，冻结代码不改（协调人同意），按各自段数重截后的比较原样保留在上面；
- 这件事不影响任何评估数字：评估只用每局的成败和整局记录，不用 K3 的截取。
