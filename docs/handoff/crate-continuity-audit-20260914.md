# 双臂视觉专家连续性自检 — 2026-09-14

结论：当前 assisted whole-body 专家尚未达到“走近、弯腰抓取、抬篮站直自然衔接”的要求。
关节限速和同一个参考控制器没有保证任务进度连续；到桌后的弯腰启动较晚，
抬篮转站直出现回落，末尾验收也占据了较长的录像时间。本次先完成自检，控制策略未修改。

## 已确认的实现机制

### 到桌 → 弯腰

[VisualApproach](../../src/locomani/tasks/crate/visual_approach.py)在 stop distance 内切换到
`settle`，同时把运动指令设为零。过滤后的目标相对速度低于 0.06 m/s、角速度低于
0.2 rad/s，并连续满足 profile 的 0.3 s，才允许接管。
成功轨迹第一次满足速度门槛发生在停止指令之后约 1.14–1.26 s；这部分既包含真实减速，
也包含滤波响应，不能全部作为空白等待删除。

[expert.py](../../src/locomani/tasks/crate/expert.py)在此期间反复发送固定上肢姿态。
ready 后还需要支撑检查、POSE 接管和新相机观测，记录中 ready 到 reach 间隔为
0.28–0.36 s。[StreamedArm.start](../../src/locomani/backends/sonic/streamed_arm.py)
包含两次各 0.1 s 的缓冲填充/保持，其时间基准为 wall time。
该接管没有旧 VR 中间阶段，但并非没有时间成本。

[CoordinatedReach](../../src/locomani/tasks/crate/coordinated_reach.py)的 reach 以双手位置和
姿态插值为主，`torso_target` 在此时仍为 None。
[WholeBodyIK](../../src/locomani/tasks/crate/whole_body_ik.py)允许髋部/腰参与，但没有为 reach
明确指定与手同步的躯干进度。因此“允许弯腰”和“从一开始就协调弯腰”是不同实现。
实测的先动手臂、稍后明显弯腰符合这条机制；各约束/跟踪误差的贡献尚未通过消融隔离。

### 抬篮 → 站直

`lift` 等待 `lift_seconds=4` 且满足升高与附着判据后，才进入 `stand`；
后者重新创建手部起点、躯干旋转插值和姿态恢复目标，时长为 `stand_seconds=5`。
两段都用独立的 quintic blend，其目标进度在各自端点速度为零。
实际关节还会受反馈和求解器影响，所以这不代表所有实发关节速度恰好归零。

回落是实测事实，不能只归因于计时器。在进入 stand 的第一个样本，
参考躯干比测量躯干多前倾约 1.97–6.26°；最初 2 s 的测量躯干又比入口多前倾
约 1.10–5.47°。参考/实际误差、手部目标重建和姿态目标变化都是应验证的解释。
尚未证明其中哪一个单独造成回落；已有结果不能称为单调、连续的起身。

### 新发现：相机更新与实际发送速率的接缝

有效新相机帧路径发送 `arm._push(q, reference_velocity=body_command.velocity)`。
重复帧或缺帧路径发送 `arm._push(arm.q)`；发送器默认把未给出的速度写成零，
并将该帧作为新的 frame index 放进 POSE 缓冲。

用实际记录的第 141 帧构造三个发送调用，通过真实的 `StreamedArm` 和
`AgentCommander.pose_chunk` 检查序列化前的包，替换网络传输为 Mock：
关节最大速度依次为 **0.63867 → 0 → 0.63867 rad/s**。
按包的 20 ms 帧间隔，速度跳变量相当于 **31.93 rad/s²**；
高于规划器配置的 2 rad/s²。这证明发送接缝未保持规划器的速度连续性保证。

这是有条件的 CPU 复现。原 `observations.jsonl` 只在新视觉决策时落行，
没有完整记录重复/缺帧补发包，无法用该日志计算真实发生频率，也无法据此认定它造成了
当前视频中的抖动或回落。应补实发包审计，再验证物理影响。

## 对 VLA 数据的含义

观察到的等待、先降后升和补发机制都值得修正，但本次没有训练实验，不能断言 VLA
已经或必然学会停住。推断风险在于：如果专家在相似图像/机器人状态下反复维持姿态，
直到隐藏阶段时间到达才运动，模仿学习会同时看到保持与继续的标签；历史/动作块可能
帮助解释，但没有消除不必要的专家等待。

原始录像的最终 hold 是成功验证，不应自动全部变成训练目标。
保留完整原片和验收记录，之后通过显式训练终点标记选择监督区间；无需剪掉中间等待
来伪装策略变连续。三相机 MP4 使用名义 25 FPS，本次一律用 JSON 的物理时间测量；
正式数据必须对齐图像、实际动作和时间，不能把视频帧序号直接当作控制时钟。

当前 visual whole-body `--record` 仍被拒绝，实际 64 维 token/历史、双夹爪及完整姿态
导出尚未验证。本批数据是专家视频/控制 pilot，不是已验证可直接训练的 LeRobot 数据集。

## 下一步修改与验收范围

1. **先修控制更新与发送接缝。** 视觉负责更新可见目标，控制按物理时钟连续执行有限时效的
   参考；每个实际发送包都记录位置、速度、root、夹爪与时间。新鲜度过期仍需受控停止，
   不能靠永远延用不可见目标达成“连续”。同时检查位置差分与速度字段的一致性。
2. **接近、准备和弯腰重叠。** 减速阶段逐步调整双手和腕部准备姿态；可靠支撑建立后，
   在保持现有参考连续性的条件下让髋部/躯干与双手共享显式进度。保留支撑和碰撞约束，
   不能简单把 settle 与接管时长设为零。
3. **附着确认后连贯抬升并起身。** 保留小幅试提验证；通过后将双手抬升和躯干恢复接成
   一条保留速度/加速度的轨迹。对测量跟踪误差有明确处理，并检查篮子实际高度回退，
   不只检查末态站直或“仍然抓住了”。
4. **把完成验收与训练终点分开。** 原片保留稳定窗口；正式导出按带来源的终点标记选择
   监督数据，不靠隐藏剪辑或任意压缩时间消除停顿。

验证应固定当前 scene/profile/部署身份和尝试集合，对照以上时间、回落、完整实发包的
位置/速度一致性，以及实际手/躯干运动；保留全部失败。中间无任务进展超过 0.5 s
可作为需要解释的诊断标记，不能直接作为通用物理安全门槛或 VLA 可学性保证。
没有多秒无效等待、没有无理由回弯/回落，并且物理跟踪与接触仍成立，才有依据把下一版
称为更连续；最终 VLA 效果仍要闭环验证。
