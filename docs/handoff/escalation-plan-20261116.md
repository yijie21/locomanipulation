## 1. 要证明什么

机器人是 Unitree G1 人形，全身控制器是 ScaleBFM（一个学出来的跟踪器，权重冻结）。任务是在房间里走到家具前操作物体。
失败的主要原因是“手送不到该到的位置”，而之前的自我改进循环只会改抓取参数，改不动这一类失败。

机制分三级，每一级只在下一级被证明无效时才启用：

| 级 | 能改的东西 | 代价 | 升到下一级的条件（下文叫“证明”） |
|---|---|---|---|
| 1 参数 | 技能的参数（进手方向、预抓后退量、抓取选择等） | 最低，只是搜索 | 预测“这一局任何参数设定都赢不了” |
| 2 站位 | 机器人相对物体站在哪、朝哪 | 中，要学一个按场景选站位的模型 | 预测“这一局任何站位都送不到” |
| 3 能力 | 控制器本身（采数据微调） | 最高，而且可能弄坏已有能力 | 最后一级 |

失败分两类，第 2 级和第 3 级各管一类：

- A 类：控制器做得到，但站位或姿态选错了。归第 2 级，控制器不动。
- B 类：控制器确实做不到（例：ScaleBFM 手腕在柜子前最高约 1.26 m）。归第 3 级。

**论文要立的一句话**：系统能判断失败属于哪一级，并只在该级花力气；同样的预算下，比“不分级一律训练控制器”和“不分级一律搜索参数”成功率更高。

查重结论（2026-11-16）：中等重合。能守住的三点是 (i) 冻结的学习型全身控制器 + 站位选择，(ii) 同预算对照分离出“递归”带来的增益，
(iii) 用搜索的证明触发数据采集。不能再说的两点：“瓶颈在身体不在大模型”（2609.31760 已说）、“只在够得着的地方有数据”（SAGG-RIAC 2013）。
HITCH（2611.08039）的做法是处处继续训练跟踪器，它是第 3 级的直接对手。

### SIMPLE 的时限：实测（2026-11-17）

官方的计时方式（本地检出 `third_party/SIMPLE`）：时限是 50 Hz 的步数，写在任务文件的 `max_episode_steps` 里；开局等机器人站稳的最多 300 步不计时
（`eval_decoupled_wbc.py:399-403`）；谓词一成立这一局就结束（同文件 441 行）。所以要比的是“到成功的时间”。

阶段 A-S 已经按这个方式计时，在 900 个练习回合上实测（真值赛道；细节、相机赛道、每段用时见[阶段 A-S 记录](escalation-a-s-20261117.md)）：

| 任务 | 官方时限 | 原脚本到成功的中位用时 | 原脚本在时限内 | 删白等 + 一组温和提速后 | HITCH 成功回合平均用时（它用 45 s 时限） |
|---|---|---|---|---|---|
| XMovePick | 16 s（800 步） | 9.6 s | 149 / 150 | 149（7.3 s） | 12.3 s |
| XMoveBendPick | 16 s（HITCH 论文表 VII；本地没有任务代码） | 10.6 s | 150 | 150（7.8 s） | 14.0 s |
| TabletopGraspMP | 16 s（800 步；HITCH 的表写 27 s，以上游最新版为准） | 14.4 s | 149 | 150（10.0 s） | 14.2 s |
| BendPickMP | 8 s（400 步） | 11.2 s | 0 | 150（6.9 s） | 16.3 s |
| Handover | 16 s（800 步） | 23.8 s | 0 | 133（15.0 s） | 31.4 s |
| PickBetweenTables | 24 s（1200 步） | 31.6 s | 0 | 132（21.0 s） | 31.6 s |

- 原脚本不加时限 884 / 900，按官方时限 448 / 900。11-17 早些时候从代码常量推的估计（约 85 / 180）偏乐观：真值赛道上每段走路末尾还有一段约 2.5 s 的纠偏，没有算进去。
- 白等的有三处：走完之后重复的 0.5 s、合指和松指实际以一半的速度在跑（`Motor.hold(0.02)` 会走两步）、抬起后的 1.0 s。删掉后成功数不变，每局省 1.5–3.5 s。
- 其余靠速度参数：走路末尾纠偏的时限、伸手和抬起的速度、转身的速度。手定一组温和的值，真值赛道 864 / 900 在时限内，不加时限的成功数从 886 掉到 869。
- 相机赛道上 PickBetweenTables 还进不了时限（转身找篮子、停下来看第二眼），要改流程。
- HITCH 在 BendPick、Handover、PickBetweenTables 上的平均用时也都超出官方时限，所以按官方时限做下来的数，它那一类方法里目前没有。

### LocoManiLab 还差什么

已知（只读了代码，没有运行）：主仓库是一层壳，仿真器在子模块 `humanoid_benchmark`（robosuite 环境），控制器和 G1 模型在 `g1_backend`；Python 3.11、`mujoco==3.3.1`。
ScaleBFM 已经接好（指令是参考根位姿 + 29 个关节 + 两手各 7 个关节，权重 13 MB 在 Hugging Face）。场景资产 3.4 GB。门和抽屉是真的 MuJoCo 关节。
真值可以从环境对象里直接读；头部深度图传 `camera_depths=True` 就有。作者自己的文档说闭环仿真这条路没有端到端复验。

| 缺口 | 细节 |
|---|---|
| 没人确认它能跑 | 第一件事是把官方的一次闭环评测跑通 |
| 我们的技能怎么驱动它的机器人 | 两条路。**沿用它的 ScaleBFM 后端**，我们的 Motor 只产出参考位姿发过去（小改动）；或者换成我们自己的运行时（中等工作量，还要对齐机器人模型、增益和权重版本，是否同一个权重没核实） |
| 评测入口是给 VLA 的 | 官方用一个 ZMQ 服务按 GR00T 协议每 20 步问一次 `get_action`。我们的技能是逐步闭环的程序，要么包成这种服务，要么自己写评测循环直接调环境和官方谓词（要在报数时写明） |
| 大量穷举跑不快 | 每次重置都重编译场景，没有不渲染的模式，唯一的速度数字是每秒 51–56 步（约等于实时），`reset()` 不带种子，没有存取状态的接口（任务计数器和控制器缓冲在 MuJoCo 状态之外）。`memo` 用不上，除非把它编译好的场景导出来在我们自己的运行时里跑 |
| 场景适配 | iTHOR / Holodeck 的房间要转出 `objects`、`surfaces`、`room`。它的数据生成器里有占用格、A* 导航、手腕目标、站距选择、Dex3 的脚本抓取（`planner.py`、`scene_frame.py`、`grasp_pose.py`、`grasp.py`），可以借 |

| 组合任务 | 132 个，要把几步串起来，第一批不做 |
| 成功判定 | 是 Python 类加每个场景的 YAML 标定，要么直接调它的，要么移植 |
| 从指令到目标 | 任务是一句话。真值赛道从任务定义里取目标；官方赛道要从指令里找物体（`blind.py` 用 SAM 3 按物体名分割，可以沿用） |

对两个基准的含义：

- **SIMPLE 官方赛道**：能做，路已经通到 148 / 180。剩下的是把官方环境（双目算深度）跑完六个任务。
- **LocoManiLab 官方赛道**：官方只给一张 320×240 彩色图，没有深度。我们的链路每一步都要深度。两条路：

## 7. 分阶段任务

### 7.0 统一的回合接口

三级机制只认这一个接口，每个基准写一个适配器 `escalation_20261116/bed_<simple|lml>.py`。

```
run(episode_id, setting: dict, stance: dict | None, controller: str = "frozen", track: str = "truth") -> record
```

- `episode_id`：一个固定的回合。同一个回合重跑必须得到相同结果（先验证，见阶段 A）。
- `setting`：第 1 级的参数覆盖，空字典是种子技能的默认值。
- `stance`：第 2 级的站位覆盖，`None` 表示技能自己选。字段：`d`（相对默认站距的增量，米）、`t`（沿家具前沿的横移，米）、`yaw`（相对正对前沿的转角，度）。
- `controller`：`"frozen"` 或第 3 级训练出的权重标签。
- `track`：`"truth"` 读物体真值位姿；`"official"` 只用官方给的输入（LocoManiLab 上另加头部深度，见第 5 节）。
- `record` 至少有：`success`（官方谓词，并且在官方时限之内成立）、`t_success`（谓词第一次成立的仿真时刻，秒；没成立是 `None`）、`loss`（下表七类）、
  `palm_err_cm`（合爪前手掌离目标的距离，真值，只用于记录）、`fell`、`stance_used`。

| 失败类型 | 含义 | 归哪一级 |
|---|---|---|
| `deliver` | 合爪前手掌离抓取位姿超过 2 cm，或手臂被挡、够不到 | 第 2、3 级 |
| `grasp` | 手到了但没抓住、抓住又掉 | 第 1 级 |
| `collide` | 途中把物体或邻居撞走 | 第 1、2 级 |
| `fall` | 摔倒 | 第 3 级 |
| `perceive` | 目标找错、抓取位姿估错（只在官方赛道出现） | 不归本机制 |
| `place` | 抓起来了、送到了、松了手，但物体没在容器上放稳 | 第 1 级 |
| `timeout` | 动作本身做成了，但谓词成立的时刻晚于官方时限（不加时限就算成功的那些局）。到时限还没做成、而且不加时限也做不成的，归上面六类 | 第 1 级（速度、等待）；没有设定来得及，归第 2 级（站得近、少走一段）；再不行归第 3 级 |

### 7.5 阶段 E：递归对照（在第 2 级上做）

目的：分离出“分代采样”本身的增益。现有的机器人自我改进论文都没有这个对照。

总预算 B 回合 = 阶段 B 第 3 步在训练那一半上实际用掉的回合数。三个组预算相同，在同一批留出回合上比：

| 组 | 做法 |
|---|---|
| 递归 | 分 3 代，每代 B / 3。第 0 代站位随机；之后每代用当前模型，在预测胜率最接近 0.5 的（回合，站位）上采样，再重训 |
| 一次采完 | 第 0 代的 B / 3 训练出模型，按同样的规则一次采完剩下的 2B / 3，训练一次 |
| 随机 | B 个（回合，站位）全部随机，训练一次 |

每组 3 个随机种子。报成功数、递归组减一次采完组的差、种子间的标准差。差不显著也照实写。

### 和榜上方法比，怎样才算公平

榜上的 VLA 是“采示范 → 训练 → 冻结 → 评测一次”。我们是“在练习回合上迭代 → 冻结 → 评测一次”。迭代相当于它们的训练，评测那一步两边一样。
要守住的是迭代用了什么，不是迭代了几轮。五条：

1. **迭代只在练习回合上做。** 官方评测回合的种子、LocoManiLab 没见过的任务和场景，迭代期间不跑。
2. **冻结后只跑一次。** 技能包、参数预测器、站位模型、控制器权重在阶段 G 之前定版，记下哈希；阶段 G 之后不再改。
3. **报出迭代花了多少。** 练习回合数、仿真步数、大模型调用量，和 VLA 的示范数并排写（LocoManiLab 的训练集是 14,160 条遥操作示范、51.5 小时；HumanoidArena 每任务 100 条）。
4. **报“没迭代”的那一行。** 种子技能直接上考卷的成绩，就是“部署上去推理一次”的数，和迭代后的数并排，差值是迭代带来的。
5. **写明迭代期间用了什么特权。** 练习时读仿真器真值、任意重置、用官方的成功判定当反馈；考卷的官方赛道上这些都不用。

先例：BiGym 2.0 给写程序的 agent 每个任务 10.1 万仿真步，冻结后的程序在 100 个隐藏种子上评测；RoboScript（2611.12885）在 RoboTwin 2.0 里排练后和 VLA 比；HITCH 在 SIMPLE 上报“每任务 5 条示范”的版本。

最干净的一组数是 LocoManiLab 的“没见过的任务 / 场景”：我们在上面零迭代，VLA 在上面零训练，条件对等；VLA 在这里只有 15–25 %。

## 11. 风险

- **LocoManiLab 的接入量最大，也最不确定。** 仓库很新（3 次提交），README 自己说没有全部复验。阶段 A-L 第 1 步先确认官方环境可用，不可用就停下来报告。
- **SIMPLE 上的缺口主要是时间，给第 2、3 级的空间很小。** 练习回合上种子技能不加时限 886 / 900，按官方时限 449 / 900；调速度以后 864 / 900（真值赛道，2026-11-17 实测）。剩下的三十几局里只有 Handover 的“左手把篮子扫走”是站位问题。SIMPLE 能展示第 1 级，站位和控制器的故事要靠 LocoManiLab。
- **站位太敏感。** 阶段 B 第 4 步为它而设。
- **第 3 级训不出来或弄坏已有能力。** 见 7.6 第 4 步。
- **我们的做法不是榜上的那类条目。** 两个基准的榜都是用示范训练的端到端策略。我们不用示范训练策略，但换了控制器、用了真值或深度。每个数旁边都要写清用了什么。
- **只有一种机器人。** 计划没有解决。
