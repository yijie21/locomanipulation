Every grasp step goes through `stage()` (src/locomani/tasks/scene/stage.py, [scene-stage]): the motor call, a check of the measured state after it (`stance_check`, `reach_check` with its stall ratio, `grip_check`, `lift_check`, or your own) and an `on_fail` action (re-walk, re-approach, open and grip again, or give up), within the round's retry budget; tune the thresholds and actions where the evidence says so. `src/locomani/tasks/scene/graspability.py` tells, without simulating, whether an object fits the open jaw on each side and how far to turn so one that fits faces it ([scene-classes]): use it to choose the grasp and the stance instead of hard-coding a width. `locomani.tasks.scene.choose.choose(world, key, start_xy)` ([scene-classes], TODO 33.12) lists every (grasp, hand, stance, posture) that stands clear of the furniture and scores each with the body model `locomani.tasks.scene.body.reach()` (the odds the controller lands the hand 3 cm or more off, from 15,120 measured reaches; a straight-down wrist at table height is not delivered, a 45-degree one is), best first, standing before a lowered pelvis before a preparatory action: call it from the skill to pick the stance, the hand and the grasp attitude it returns (`Option.att`, `stance_xy`, `stance_yaw`, `grasp_xyz`, `pelvis_z`), and write the grasps and preparatory actions it asks for; it is infrastructure, not yours to edit. When it says `needs_prep`, `locomani.tasks.scene.prep.select(world, key, start_xy)` ([scene-prep]) names the goal to reach first -- turn the object by so many degrees, move it so far toward an edge, move a neighbour aside -- with the chooser's option after it; write the action as a skill function `run(ctx, plan) -> Outcome` registered with `@prep.register("turn" | "pull" | "clear")` (the motor layer's reach, grip, release, sidestep; `prep.met(plan.goal, pos, quat)` says whether the measured pose reached the goal), then choose again on the measured state. The goals, the selector and the registry are not yours to edit. In a scene with movable floor furniture (the scene file's `movable`; [scene-prep]) a goal of kind `floor` names a chair or stool (`plan.goal.key`) to move to `plan.goal.pos` along `plan.goal.direction_deg`: write that action too, `@prep.register("floor")`, and call `locomani.tasks.scene.floor.refresh(ctx.world)` once the piece has moved, before walking anywhere, so the map shows where it now stands. `choose.two_hand(world, key, start_xy)` lists a two-hand clamp's stances with each hand's odds. A grasp can be written as constraints on an object's points instead of a hand-built pose ([scene-keypoints], TODO 33.9): `locomani.tasks.scene.keypoints.pick(ctx, key, spec)` with e.g. `dict(pinch=("hull:-y", "hull:+y"), twist=45)` or `dict(centre="top", approach="down", closing="horizontal")` plans the grasps, ranks them with the chooser and the body model and executes the best through stage(); `keypoints.plan` gives the options, `keypoints.execute` runs one, `scripts/rsi/keypoints.py <scene> <object> --points` / `--spec JSON` shows what a spec gives without simulating. Write which points and constraints a kind of object takes, by its geometry. A parameter a design probe has measured ([scene-probe]) can be asked for instead of written down: `body.best_level("module.NAME", task)` returns the measured best level, or None when no level clearly beats the others -- then keep your default ([scene-classes], TODO 33.1.7). Round records carry `failure_class` and `events`; read them on the rounds you target.

When the Manager's decision is `reopen`, the context holds `park` (the claim, its exits, what code checked) instead of a hypothesis: build the exit the Manager names as a skill path that the parked starts take, and smoke it on one of them. The loop first runs the candidate on that park's diagnostic starts; only if it finishes one does the candidate reach the gate, where it must still not lose other starts.

Recipes and files: You may change only files under {SKILLS}: change parameters, add or rewrite skills, add modules (they import each other relatively; `plan_for(task)` decides which skill a goal uses; parameters meant for overriding are upper-case module constants). Any other changed file voids the candidate. Code must be deterministic. A flow for one object or one kind of object is allowed ([branch]): put it under `recipes/` with a `SIGNATURE` of the features it is for (hull width at the grasp height, height, flat or tall, container, wall, mass, friction, support height, a cover above) and `match(obj) -> score`, chosen by features in the package's dispatcher, with the generic pick as the fallback, so it serves similar objects later. Never select by an object's name: a string constant equal to a scene object's key, body or name stem (Mug_2, Mug_2_object, Mug) anywhere but a docstring voids the draft.
