Scene tools (read their --help before use):
- `{SIM_PY} scripts/rsi/graspability.py --help`: without simulating, whether an object fits the open jaw on each side, how far to turn so a side that fits faces the jaw, and which preparatory action would make it fit ([scene-classes]). Use it to check a too_wide or knocked round's geometry before proposing a grasp change.
- `{SIM_PY} scripts/rsi/body.py reach --help` and `{SIM_PY} scripts/rsi/choose.py --help` ([scene-classes]): the body model says, from a table of 15,120 measured reaches, how likely the controller is to land a hand 3 cm or more off a target (forward, outward of the hand's side, height; level, tilted or straight-down wrist; standing or lowered pelvis) -- AUC 0.78 on this line's pre-grasps against 0.60 for the IK residual; the chooser lists, for an object at a start, every (grasp, hand, stance, posture) that stands clear of the furniture with those odds, best first, and the fallback order (standing, lowered pelvis, a preparatory action). Use them to say whether a failed reach was ever deliverable from where the skill stood, and what it should have chosen. Every one-hand reach step in a round record already carries the model's prediction for its command, made before the arm moved: `pred_p_miss`, `pred_err_cm`, `pred_att` (the wrist attitude it read from the command), `pred_inside`, and `pred_open` (false when the jaw was already closed on something, outside what the table measured).
- `{SIM_PY} scripts/rsi/keypoints.py --help` ([scene-keypoints]): an object's named points and, for a set of keypoint constraints (a pinch across two points, an approach, a closing axis, a twist), the grasps they give, ranked by the chooser and the body model, without simulating.
- `{SIM_PY} scripts/rsi/prep.py --help` ([scene-prep]): for an object the chooser cannot serve, which preparatory goal (turn it, pull it toward an edge, move a neighbour out of the corridor, or -- in a scene with movable floor furniture -- move a chair or stool aside) would give a standing stance, and whether the skills package implements an action for it (`--skills {SKILLS}`); a kind that would help with no action behind it is a gap to name in a hypothesis or a claim's exit.

Before the probe runs, commit to predictions: which diagnostic rounds (their labels) will flip from failure to success, and which successes might break. Your hit rate is measured. Give each hypothesis `instead`: in one sentence, what to change (the skill, the step, the rule). The driver sets its `status` from the probe ([scene-status]); a mechanism proposed in two or more iterations and not refuted is built, so name a repeated mechanism the same way each time. When the test needs code but the claim is about a measured quantity ("the soap fails when the jaw closes across its wide side"), give it a `measure` over a column of the record library -- every round you may see, from this run and the finished ones, one row each: `{SIM_PY} scripts/rsi/records.py features --task <task>` lists the columns and their ranges, `{SIM_PY} scripts/rsi/records.py query <feature> <op> <value> --task <task>` shows the split. The driver then sets the status from the incumbent's own rounds; a correlation decides what to build first, not what stays. When the context carries `attribution`, the driver has already run each recurring failure's failing command alone from the same start ([escalate]): a `motor` round fails with nothing of the skill around the command, so do not propose a fix inside the motor layer for it -- propose a way around it, or leave it. When the diagnostic rounds tangle several factors together (where the robot stood, how far it spawned, which way it faced, how the object lay), ask for a `design` probe instead of guessing ([scene-probe]): one factor at a few levels on the same starts, at most 300 rounds (levels × starts × tasks); the result reaches the Manager this iteration and you the next (`designs_last`). A level that left out more than half its starts (the result's `note`; the reasons in `skipped_why`) says little: pick other levels, other starts or another factor rather than asking for the same probe again. To see whether one motor primitive does it alone -- a turn in place of so many degrees, a walk of so many metres, a sidestep -- with no skill and no task around it, ask for factor `primitive` with `name` walk / back / side / turn: one run per level on the empty floor ([scene-probe]).

Parameters are searched by the program; you name the knobs. Besides `delta.set` (the values you fix), a hypothesis may carry `sweep`: at most 2 items {"key", "values": [2 to 5 values]}. The program runs each value on the starts of the hypothesis's tasks (the second key with the first held at its best), compares each run with the incumbent start by start, and keeps the best value: the most starts fixed minus broken; ties go to fewer broken, then to the earlier value in your list. Give values that bracket the change you expect, taken from the quantity the value comes from; do not tune a number to particular episodes. The probe result then carries `sweep` (a table: key, value, n, fixed, broken, net) and `best_set`. A hypothesis whose mechanism needs code (`needs_code`) is not probed at all: its status is `untested`, which is not a refutation. Keep proposing `tasks` for every hypothesis: the probe and the sweep run only on those tasks' starts when the family's caps say so.

Infeasibility (plan section 8, D13; [scene-park]). When the evidence says some starts cannot be done with the kinds of action the skills have now, put a claim in `infeasible`; never drop the starts. "Cannot with the present actions" is not "impossible": say which actions you considered and what new action would open the starts. A claim has:
- `task` and `starts`: diagnostic labels of that task (all of them for a task-wide claim);
- `kind`: `current_skills` (the present kinds of action cannot) or `physical` (no action could: out of reach, over the payload, inside something that cannot open; only the user can confirm this, until then it is handled as current_skills);
- `actions_assumed`: the kinds of action you considered (for example side and top-down grasps only);
- `bound`: `statement` (the hard constraint in one sentence, with its numbers) and `check`, the path of a Python file you write in {TMP} that defines `check(start, meta) -> {"holds": bool, "value": ..., "limit": ..., "note": ...}`. It must compute the constraint from the start row (`task`, `start`, `label`) and the scene file `meta` (scene_meta.json, already parsed), not hard-code the answer; the driver runs it on the task's diagnostic starts;
- `exits`: at least one `{"capability", "how"}`, where `capability` is a short reusable name (for example "pre-grasp tilt", "slide to the edge", "move the neighbour first") and `how` says how it would make these starts doable; a `physical` claim may give `no_exit_reason` instead;
- `refuted_by`: the result that would prove the claim wrong;
- `attempts`: 1-3 parameter override sets (`{"name", "set"}`), the strongest the present skills can try on these starts; the Prober runs each closed loop on the claimed starts.
Code refuses a claim that lacks a part. A claim parks its starts only if the check holds on every claimed start and no attempt succeeds. Parked starts still count as failures in every pool; you need not target them, and they reopen by themselves when an incumbent finishes one (the claim is then recorded as wrong). The parks so far are in the context's `parked`.
