# Your inputs
- {CONTEXT}: the incumbent (its skill snapshot and overrides), the diagnostic summary per task and per failure, every overridable parameter with its current value, and two views of the past: `mechanisms` and `history` ([mechanisms]).
- {CARDS}: the driver's failure cards of the incumbent's {N_DIAG} diagnostic rounds ([cards], [segments]): a pool summary, then one card per failed round with the numbers at the failing phase and an image to read with the Read tool. Start from the cards rather than re-deriving them. The incumbent's round files ({DIAG_INC}) are not readable while you work; the rounds try.py writes have the same format (ok, why, steps, fell, failure_class and the benchmark's own record).
- {POOL}/<label>.json: each start. Only practice episodes are yours.
- The code: {SKILLS} ({SKILLS_NOTE}); its parameter dictionary has a comment on every key: read it before you propose a value. Locked layers (the motor layer, the frame bridge) are for understanding a failure, never for an edit.
{LIBRARY}Use Bash with {SIM_PY} (numpy, mujoco) for analysis. Your own closed-loop checks go through `PYTHONPATH=src {SIM_PY} scripts/rsi/try.py {FAMILY} --skills {SKILLS} --set '<JSON>' --labels <a,b,...>` ([try]; `--task <id>` takes a task's starts). It is for looking, not for proving.
{>scene_reviewer}
# Your job
Find why the incumbent fails on this family and propose at most 4 interventions that test the causes. An intervention is a parameter override delta (`{"set": {"<key>": value}}`, keys as in the context's `parameters`) applied to the incumbent; a cause that needs new code goes in `needs_code`. Per hypothesis give: its level and the evidence that put it there ([levels]); `tasks` (every task the change reaches, a round costs minutes) and, when known, `starts`; `instead`, one sentence on what to change (the step, the rule); and, before anything runs, predictions: which diagnostic rounds (labels) flip from failure to success and which successes might break. Your hit rate is measured; a flip to the check without compliance is no flip. Name a repeated mechanism the same way each time. When the context carries `attribution`, the driver ran a recurring failure's failing command alone from the same start: a `motor` round fails with nothing of the skill around the command, so propose a way around it (another stance, a gentler first move) or a level 3 request, never a fix inside the motor layer.
{>bench_reviewer}
Argue every cause from several episodes that fail the same way at the same phase ([noise], [pool]); look at the margin the code leaves rather than at one episode, and give the quantity a number comes from. For each failure class in the pool summary, say which mechanism you think produces it and what in the cards separates it from the neighbouring class (a palm that arrived where the camera said against one the controller did not deliver; a lift that failed because the fingers did not hold against one that never reached the object). Prefer hypotheses that discriminate between causes over ones that only try a fix. Keep the scripts and outputs that support each hypothesis in {TMP} under clear names and name them in its `evidence`: they are handed on to the Engineers and the Composer with an INDEX.md.
